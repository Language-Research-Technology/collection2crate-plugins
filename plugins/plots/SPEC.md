# Plots plugin specification

Implement a visualisation-only plugin named `plots`. It integrates the local
[`ro-crate-plots`](https://github.com/Language-Research-Technology/ro-crate-plots)
package with collection2crate's Visualise page, using tabular data already
provided by the host (especially tables generated by roctable).

## Scope and plugin contract

- Export `createPlugin()` from `index.js` and return
  `{ name: "plots", visualisation: { ... } }`.
- The panel label and heading should be `Plots`; its hint should explain that
  it builds Vega/Vega-Lite plots from loaded RO-Crate tables.
- This is a visualisation plugin: declare no build hooks and do not write plot
  data, generated HTML, or other exploratory output into the selected folder.
- Read the host-provided `ctx.tables` (`{ source, header, rows }`); do not read
  CSVs or the filesystem to obtain datasets. Convert each table's header and
  rows to the array-of-objects shape accepted by ro-crate-plots.
- Declare `ro-crate-plots` as a pinned Git dependency and use `npm link
  ro-crate-plots` against the local clone during development. Do not commit a
  machine-specific file URL. The browser map adapter lives in this plugin
  because upstream's map renderer depends on Node canvas and filesystem APIs.
- Register `plots` in the plugin registry and keep it selectable through the
  host's normal plugin-selection process.

## Configuration storage and editor

The plots library uses a JSON configuration with a top-level `plots` object.
Persist the plugin's config at `_config/plots/config.json` in the selected
collection folder, following roctable's persistent `_config/<plugin>/`
convention. Keep the config-editor implementation in a source `config/`
directory under `plugins/plots/` (for example, `plugins/plots/config/`). The
config folder in this plugin source is for editor modules; `_config/plots/` is
user data in the selected collection folder and must survive rebuilds.

- On first open, create a default config bound to the currently loaded tables
  and open the config editor. Reopen it from a visible **Configure plots…**
  action at any time.
- Use the host's modal and folder read/write APIs, following roctable's
  `config-tree-ui.js` and `openConfigTreeEditor` approach. The host passes the
  selected `dirHandle` in `ctx`; the plugin receives `openModal`,
  `readFileTextFromDirectory`, and `writeFileAtPath` through `createPlugin(deps)`.
  Do not access Node's filesystem from the visualisation or save config to
  browser storage or an unrelated output directory.
- Edit a working copy. **Save** validates and persists the config;
  **Cancel** leaves the saved config unchanged. Invalid JSON, missing required
  fields, an unavailable dataset, or invalid plot-function arguments must be
  reported in the editor without destroying the last valid config.
- The editor must support multiple plots, add/remove, reorder, title, dataset,
  display width, and plot-specific settings. Each plot independently selects a
  named dataset, so any number of plots can reuse the same table-backed dataset
  without duplicating its data or adding another dataset entry. The **Add plot**
  control must let the user choose the dataset for the new plot and should
  default to the most recently used plot's dataset when possible.
  Use compact, task-oriented controls and allow advanced JSON editing where a
  typed form cannot faithfully represent a library option.
- Refresh the available table/dataset choices from `ctx.tables` whenever the
  panel is opened. If an existing config names a dataset that is no longer
  loaded, keep and identify that config entry so it can be repaired; do not
  silently rebind it to a different table.

### Config model and feature coverage

Preserve the ro-crate-plots configuration shape and all its current features:

- `plots.globalConfig`: arbitrary Vega Embed options shared by every plot,
  overridden by that plot's `config` values. Support editing it as validated
  JSON and provide controls or documentation for common options such as
  `actions`.
- `plots.datasets`: named datasets bound to loaded tables. Offer each source
  as a choice, permit a stable user-facing dataset name, and convert rows to
  objects using their corresponding `header` values. Dataset paths in the
  standalone package config are not used to load host data in this plugin.
  A dataset name is a reusable reference: multiple `plotList` entries may
  point to the same `dataset.name`, and the table's row objects are prepared
  once for the panel render and shared by all plots that reference it.
- `plots.plotList`: ordered plot cards, each with a dataset, a plot builder or
  custom Vega/Vega-Lite spec, generated spec, per-plot embed `config`, title,
  and layout span. Preserve unknown fields when loading and saving so newer
  ro-crate-plots features are not erased by this editor.
- Offer every currently exported builder from `ro-crate-plots/index.js`:
  `barPlotCount`, `scatterPlot`, `boxPlot`, `histogramPlot`, and
  `plotMapHeatmap`. Generate each builder's argument controls from its actual
  supported arguments rather than presenting irrelevant fields for every plot
  type. Include data-field selectors populated from the selected dataset,
  field types, axis/tooltip titles and labels, temporal units, color field and
  palette, plot title/subtitle, and histogram bin settings where applicable.
- `plotMapHeatmap` must expose latitude, longitude, and optional weight column
  mappings (converted to `lat`, `lon`, and `weight` rows), bandwidth,
  contour count, opacity, palette, zoom, map provider, and target image size
  settings. The plugin's browser adapter uses browser canvas/fetch and a bounded
  in-memory tile cache, while preserving and displaying required map-data
  attribution. Tile/network or canvas failures must be reported for that plot.
- A custom spec editor must support arbitrary valid Vega or Vega-Lite JSON,
  including embedded values. When a custom spec is active, preserve it and do
  not overwrite it by regenerating `generatedSpec` from `makeSpec`.
- The library's example config uses `plotCardSpan`, while its HTML template
  currently checks `plot.span`. Reconcile this mismatch in the integration so
  the saved config and rendered layout agree; do not silently discard the
  user's selected card width.
- Generated Vega specs may be cached back into the saved config only after a
  successful generation, without modifying source datasets or user-authored
  custom specs.

## Plot rendering

The standalone `renderTemplate()` reads paths from disk, renders a Nunjucks
HTML file, and writes that file. The visualisation panel must not use that flow
or write standalone dashboards as part of normal panel use. Instead:

1. Bind configured dataset names to the corresponding in-memory `ctx.tables`
   data converted to row objects.
2. Call the selected exported builder from the linked `ro-crate-plots` package
  with the configured arguments and in-memory data; use the browser adapter
  for `plotMapHeatmap` because the upstream implementation is Node-only.
3. Render the resulting Vega/Vega-Lite specs into the panel, honoring global
   and per-plot embed options, plot ordering, title, and card span.
4. Keep all result rendering in the panel. Report per-plot generation or embed
   errors in that plot's region while allowing other valid plots to render.

The panel should clearly handle no tabular output, no plots configured,
missing datasets/columns, invalid custom specs, and plot generation or embed
failures. Re-render after a saved config is accepted or the host supplies a
new table set; do not reread the folder's CSVs.

## Testing requirements

Keep data conversion, config validation, plot generation, and error handling
independently testable where practical. Add focused tests for:

- Converting `{ header, rows }` host tables to named ro-crate-plots datasets,
  including empty tables and missing/duplicate field names.
- Validating and preserving the ro-crate-plots config shape, unknown fields,
  custom specs, and ordered plot entries.
- Generating builder specs with table-backed in-memory data and merging global
  and per-plot Vega Embed options with per-plot values taking precedence.
- Handling the `plotCardSpan`/`plot.span` layout compatibility.
- Reporting missing table data and per-plot generation/render errors without
  hiding successful plots.

Add focused tests for these behaviors as part of the implementation. Keep tests
independent of the DOM and external network wherever possible; isolate map tile
and Vega rendering tests behind injected boundaries or deterministic fixtures.
